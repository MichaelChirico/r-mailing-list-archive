> On 27 Jul 2026, at 10:13, Kevin Ushey <kevinushey at gmail.com> wrote:
> 
> Hi Simon,
> 
> Would you be willing to put cmake on the PATH by default on the macOS
> CRAN build servers? Or, if you wanted to be judicious, do so only for
> packages which declare SystemRequirements: CMake in their DESCRIPTION?
> 


For the latter, the VM setup is not conditional, so we certainly don't want to mess with the setup as-hoc - it should stay reproducible.

To the former, I'm a bit surprised this is even an issue, since this is the status quo for years and has been always documented, so it boils down to people not bothering to read the manuals. The main reason for cmake not being on the PATH is that CMake officially doesn't do that so we cannot expect users to mess with their PATH (it gets complicated since there is not a single place to change the PATH on macOS as R can be run from applications that don't use the profile), so the packages should be able to deal with that, otherwise they won't install for the users, either. I wouldn't want to make cmake part of recipes, because it is already maintained by Kitware, so we want to rely on official binaries where possible. This is not about CRAN machines, but the ability to install the package from sources at all.

Cheers,
Simon

Afaik, all common ways to install cmake on MacOS either default to, or
provide an option to add cmake to the path. If you installed cmake
with macports/homebrew, it is always on the path. If you used the dmg
installer from the cmake website, it is not, but there is an item in
the top menu bar: "Tools > How to install for command line use", where
it is explained what to do. I think users that install things from
source will manage.

OTOH it is quite difficult to write portable software if you have to
search all possible locations on different systems where some command
may reside if not on the path. It's not about "not bothering to read
the manuals" but just something that catches us by surprise because it
is unusual, and therefore goes unnoticed when testing on the standard
environments, where cmake is always on the path.

Hi Simon,

Thanks, that makes it clear. I'd argue that the world would be simpler
if this was pushed to users; that is, R required users to put cmake on
the PATH via some means before installing packages which use it. Users
who choose to install packages from sources on macOS are already
accepting a (potentially substantial) burden; asking these users to
have cmake on their PATH is simple compared to some other package's
requirements. But I can understand the motivation for the current
behavior.

The other pain point for package authors is that this error isn't
surfaced until after a package has been accepted on CRAN, when failing
checks are later discovered on macOS. Ideally, such an error could be
detected before submission via R CMD check. I've put up a proposal
here that would have R check for usages of plain 'cmake' here:

https://github.com/r-devel/r-svn/pull/277

I can also create a patch on Bugzilla if this is worth considering.

As an aside (also included in the changes above), I suspect this line in R-exts

if test -f "$CMAKE"; then echo "no 'cmake' command found"; exit 1; fi

should be e.g.

if ! test -f "$CMAKE"; then echo "no 'cmake' command found"; exit 1; fi

Best,
Kevin
