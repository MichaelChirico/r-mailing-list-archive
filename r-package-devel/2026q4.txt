Hi all,

I am looking for advice, how I can provide reproducibility for a design 
whose creation involves random steps for cases where the user did not 
set a seed.
My current approach, which was rejected by CRAN (I'm still trying to 
argue):

create a seed randomly via "if (is.null(seed)) seed <- sample(32000, 1)",
use that seed (instead of NULL) for design creation,
and store it with the output object.

Of course this modifies .Random.seed, but the algorithm itself also 
modifies that. The benefit is?that the user can reproduce the same 
design even if they didn't use a seed. I don't see any harm, as the user 
can also run many attempts with seed NULL and get different results each 
and every time.

I think that the reproducibility of an experimental plan is important, 
and I don't want to sacrifice that.?Are there any ideas what I could do 
instead if I cannot convince CRAN of my strategy?

Best, Ulrike

anything, and you still preserve reproducibility.

I have not had the time to answer on CRAN.

There are good reasons now to allow for changing a seed.

If generating that plan is part of a simulation. You will always set the 
seed to a rather random  place in the random number stream which may 
cause randomly starting at a place where you have been before and you 
may end up with repeated random number. Also for running in parallel: 
you won't benefit from parallel indeoendent random number streams any more.

So please don't do that.

If you want to make it reproducible, you could simply store the 
.Random.seed object (at the state before you started to generate the 
plan) with your plan.

Best,
Uwe Ligges

The easiest way to use a reproducible seed by default is to call
withr::local_seed to set the seed within the function because it will reset
the seed when the function exists.

function(..., seed = NULL) {
  withr::local_seed(seed %||% 1L)
  # rest of function
}

If you don't want to depend on withr, you can achieve a similar thing with
on.exit.

I agree with this. There is one corner case, though, that is hard to
control for: when you run in a fresh R session where .Random.seed does
not exist. Recording that state won't help reproducibility because
then R will use a "random" RNG state.

Related: The fact that .Random.seed is unset in a fresh R session
requires lots of special handling in many scenario, e.g. if
(exists(".Random.seed", envir = globalenv()) ... else ... It's been on
my wish list to have R always initiate the RNG state, avoiding this
special case that requires careful handling (and is often overlooked).

Thanks, everybody, I guess I now understand that my previous take was 
somewhat naive.

Providing a single integer as seed makes it very easy to reproduce a 
design. Providing .Random.seed is more complicated for the user to 
handle, especially for users who are not into programming. Storing the 
design itself may be not much more difficult than storing .Random.seed. 
Thus, I guess I drop the plan to enforce reproducibility if a seed is 
not provided,
and instead make the user aware why it may be particularly important to 
specify a seed.

Thanks again!

Best, Ulrike

Hi all,

now I am looking for advice on how to handle \donttest, \dontrun or 
@examplesIf.

I have various examples that would increase run time beyond 5s, but not 
dramatically so. I understand that I should wrap those in \donttest, and 
they will be occasionally checked on CRAN and be included by examples().

I have a few examples that only make sense to run interactively, as they 
require a user interrupt and would otherwise run for a very long time 
(basically unpredictably long, among other reasons because of random 
seeds). These should only be run intentionally, if someone wants to look 
exactly at that example (i.e., also not be part of an examples() run in 
an interactive session). I consider it suitable to put those in 
\dontrun, explaining why in the example comments. Is that acceptable?

I have other examples that can run automatically but will also take very 
long and should not be part of an examples() call, unless a user decides 
to have them. They should also not be run on CRAN and consume CRAN run 
time, and should not routinely be run in my own checks. I want to run 
these under the condition that the user (or the tester) wants them to be 
run, which is controlled by an option "run_heavy_examples". Following AI 
recommendation, I have thus moved those behind an
@examplesIf getOption("run_heavy_examples", default = FALSE)
tag in Roxygen, with comments for users how they can achieve that the 
example is included in an examples() run.

Does that sound reasonable, or are there better ways to handle this?

Are there rules how much example runtime is acceptable under 
--run-donttest? (Where would I find that info without having to ask?)

Best, Ulrike

>   Demos may be interactive (e.g., some await a browser response, require
>   authentication, or contain instructions for special data or software
>   setups) and are sometimes used for computationally intensive examples
>   (e.g., replication scripts from associated publications), so `R CMD check`
>   does not run demo scripts by default (similar to `\donttest` examples,
>   which are only checked with option `--run-donttest`).
>   Package maintainers could add an explicit condition such as
>   `if (!interactive()) quit()` to demo scripts that require interaction,
>   so (occasional) checks with `--run-demo` can be used to cover the others.

Dirk,

the short answer is because we care about our users.

There is still a significant fraction of users with Intel Macs (last time I checked our logs it was around 20% - arguably one of the drivers is that Apple has never made any arm64-based 27" iMacs so they are still commonly used today - they do last forever ;)). To make things worse, Apple has been dropping drivers from later macOS versions so most Intel Mac users cannot upgrade their macOS even if they wanted to and thus we cannot raise the SDK versions to the arm64 levels as the binaries would simply fail on any macOS below the SDK version (just as r-universe binaries would) due to missing run-time entry points.

Please note that the CRAN build setup is not special in any way and easily reproducible on any Mac including GitHub actions (GH provides Intel macOS runners) - all it takes is downloading the Command Line Tools for Xcode 14.3.1[1] in /Library/Developer/CommandLineTools and MacOSX11.3.sdk[2] in /Library/Developer/CommandLineTools/SDKs. For any CRAN-built dependent libraries (if needed) see https://mac.r-project.org/bin/ (specifically fetch any necessary files from https://mac.r-project.org/bin/darwin20/x86_64/ ).

That said, I have several spare Intel Macs since we only use one for the builds now, so if you need access I'd be happy to arrange it for you.

As for your test code - regardless of the SDK this that seems to fail:

$ clang++ -std=c++20 test.cpp 
test.cpp:13:26: error: no member named 'format' in namespace 'std'
       std::cout << std::format("{} ", n);
                    ~~~~~^
1 error generated.

presumably due that fact that std::format has only been introduced in clang 16. Note that, technically, full C++20 support is not present in any version of clang even today, so if you want to rely on C++20 features you'll have to navigate the minefield regardless.

As long as Apple Intel Macs see significant use, we will strive to continue to support them. Every year before the x.y.0 release we are evaluating the usage stats to see what is worth supporting, they are just not dropping as fast as you would expect. It is not my call whether failures on the x86_64 macOS platform are considered significant for packages, so it is certainly possible to move that build to a best-effort basis, but that would be a discussion to have with the CRAN team.

Cheers,
Simon
