Dear all, I'm writing you this email since I would like to ask an 
outside opinion on a design question that has come up in the development 
of the osmextract R package (https://github.com/ropensci/osmextract).

Background: osmextract reads OpenStreetMap data obtained from external 
providers (e.g. Geofabrik) via GDAL's OSM driver and returns sf objects. 
The OSM wiki (https://wiki.openstreetmap.org/wiki/Node) documents that 
lat/lon coordinates in the OSM database are stored with a fixed 
resolution of 7 decimal digits. However, at the moment, this information 
is completely ignored when reading and returning OSM data.?Therefore, 
following this consideration and the discussion in #323 
(https://github.com/ropensci/osmextract/issues/323), I drafted a PR 
(#326, https://github.com/ropensci/osmextract/pull/326) that proposes 
unconditionally calling sf::st_set_precision(x, 1e7) on every object 
returned by the package's functions, instead of leaving precision at 
sf's default of 0 (no rounding or snapping).

So my question is: do you think that this could be a good/reasonable 
idea? Or it might be rude to forcefully set a given precision level on 
the sf objects returned by the package? Are there any unexpected or 
unforeseen consequences that I'm ignoring?

Thanks for your assistance and I hope my question is clear

Dear list,

I would like to share Monolith, an open-source R/Shiny application for
analysing and mapping point-referenced data. Developed for soil and
environmental applications, it brings tools from packages including
gstat, fields, sf, terra and tidymodels into a graphical workflow,
from a sample table to model diagnostics and GIS exports. The
graphical interface is intended to support routine analysis without
step-by-step R scripting, and may also be useful in teaching through
interactive exploration of methods and diagnostics.

https://github.com/rserdarkara-hash/monolith

Interpolation methods include IDW, thin plate splines, ordinary
kriging, heterotopic co-kriging, regression kriging and random forest
kriging. Cross-validation options include leave-one-out, random folds,
spatial blocks and kNNDM. Automatic model fitting and parameter
selection are repeated within the validation folds; manually specified
parameters remain fixed. The app also includes separate modules for
descriptive statistics, correlation analysis, PCA, random forest
interpretation, and supervised multiclass classification.

Maps and diagnostics can be exported as figures, tables and GIS
layers, alongside saved settings and run records. Computation runs in
background workers, with progress reporting and cancellation.

The scope is two-dimensional point data, with isotropic interpolation
and covariates supplied as table columns. Kriging uncertainty
estimates are conditional on the fitted variogram; RK/RFK maps also
omit uncertainty in interpolated covariates. These choices and other
limitations are documented in the scientific guide and README.

The app runs locally with R >= 4.5.0 and is licensed under GPL-3.0.
The repository includes setup instructions, user and scientific
guides, a pinned renv environment, and a test suite run on Windows and
Ubuntu.

After setup, launch from the repository directory with:

shiny::runApp("monolith.R", launch.browser = TRUE)

I would welcome any feedback, particularly on the methodological
choices, usability, and behaviour on other datasets, either here or
through GitHub issues.
