If I had to guess, it's probably the lag function, as the default in
tidyverse has a one-period look-AHEAD, whereas stats::lag (the correct
function) has it one period *behind*.

For the error line, in R/Finance lingo, you'd do

returns <- Return.calculate(Ad(<<your symbol here>>))

But in any case, it's generally good practice NOT to use the tidyverse in
general, in my opinion. The data.table library is superior for general data
analysis, and it's absolutely no-go once you get to finance, since it
overrides first, last, lag, and filter functions in ways that can easily
make code break.

The only time I'd use tidyverse functionality is with ggplot2. Other than
that, the usual xts, quantmod, and PerformanceAnalytics packages should
have all the functionality you need.

Is there a particular reason you want to use tidyverse packages?

Hello everybody,

My name is Can, I am a student at Politecnico di Torino finishing up my 
Master's thesis. I am using the rmgarch package for modeling and 
simulation purposes. I am writing here today to share with you some 
unexpected behavior I observed when attempting to simulate DCC 
trajectories with an mvt distribution. I believe to have also identified 
the bug that is causing the issue. I am not terribly experienced in R or 
C++, but I have created a pull request 
(https://github.com/alexiosg/rmgarch/pull/7) with a fix that is 
seemingly straightforward. This is my first time writing to this mailing 
list, please let me know if I fail to adhere to any guidelines.

TL;DR Running dccsim with a fitted DCC model using the mvt distribution 
generates trajectories where the innovations are drawn from a 
multivariate normal distribution instead of a multivariate t 
distribution. This is caused by a certain Rcpp::RNGScope instantiation 
call within `rmvnormx`(rmdist.cpp) that breaks the chi-squared sampling 
within `rmvtx`(rmdist.cpp).

I first observed the problem when trying to simulate trajectories 
according to a DCC model fitted on my data:
1. Fitting fresh DCC models on the generated trajectories resulted in 
[Joint]mshape parameters that were consistently above 49.9 (due to the 
ceiling at 50) even though the fitted model's [Joint]mshape parameter 
was 5.367926.
2. Calculating the kurtosis of the trajectory innovations with 
`moments::kurtosis(sim at msim$simZ[[i]])` confirmed that the innovations 
used to progress the simulated trajectories consistently displayed a 
normal kurtosis of approximately 3

Upon observing this behavior I decided to look under the hood. I 
confirmed that everything read as expected all the way down to (dccsim 
-> .xdccsim.fit -> .dccsim.fit -> .dccsimf -> dccsimmvt -> rmvtx -> 
rmvnormx) `rmvtx` and `rmvnormx`. Observing that `simZ` had a direct 
connection to `rmvtx` I decided to give more attention to these 
functions.

I have not worked with Rcpp or RNGScope before, I don't know their 
working mechanisms. The problem might be obvious to those that are more 
familiar. I opted to run three experiments where I monitored the value 
of `rc` across multiple calls to `rmvtx`. I repeated each experiment 
configuration using the same set of seeds.

Experiment 1: No change to the package
Experiment 2: Removed the call to `rmvnormx` within `rmvtx`
Experiment 3: Kept the call to `rmvnormx` within `rmvtx`. Removed the 
`Rcpp::RNGScope` instantiation call within `rmvnormx`

In Experiment 1 it was observed that `rc` was indeed being assigned the 
same value across all calls to `rmvtx`.
In Experiments 2 and 3 it was observed that `rc` was assigned different 
values across different calls to `rmvtx` as intended.

It is my understanding that removing the `Rcpp::RNGScope` instantiation 
call within `rmvnormx` would be a safe fix for this problem since there 
is no random number generation within `rmvnormx` to begin with.

After applying this fix I retested to confirm that the [Joint]mshape 
parameters of models fitted on simulated trajectories as well as the 
kurtosis values of the simZ for these trajectories are in line with what 
should be expected.

My current understanding of how RNGScope works is as follows. 
Instantiating with `Rcpp::RNGScope scope` reads the current RNG state 
from R. This state is advanced as needed with any random number 
generation performed within the scope of the cpp function. When exiting 
the scope the state is written back to R.

So I guess the nested RNGScope instantiation calls, where `rmvnormx` 
does not do any random number generation, somehow result in an RNG state 
that does not advance across consecutive calls to `rmvtx`. (Does the 
scope instantiation in `rmvnormx` read the RNG state from R again 
instead of from its parent scope? Does it then somehow overwrite the 
state for `rmvtx` before the state is written back to R?)

I would appreciate any insight into the exact mechanisms that cause this 
bug and any feedback regarding the proposed fix.

Best regards,
Can Yaln?z

>>> On Sep 9, 2026, at 08:07, Can Yalniz S308980 via R-SIG-Finance <r-sig-finance at r-project.org> wrote:
>>> ?Hello everybody,
>>> My name is Can, I am a student at Politecnico di Torino finishing up my Master's thesis. I am using the rmgarch package for modeling and simulation purposes. I am writing here today to share with you some unexpected behavior I observed when attempting to simulate DCC trajectories with an mvt distribution. I believe to have also identified the bug that is causing the issue. I am not terribly experienced in R or C++, but I have created a pull request (https://github.com/alexiosg/rmgarch/pull/7) with a fix that is seemingly straightforward. This is my first time writing to this mailing list, please let me know if I fail to adhere to any guidelines.
>>> TL;DR Running dccsim with a fitted DCC model using the mvt distribution generates trajectories where the innovations are drawn from a multivariate normal distribution instead of a multivariate t distribution. This is caused by a certain Rcpp::RNGScope instantiation call within `rmvnormx`(rmdist.cpp) that breaks the chi-squared sampling within `rmvtx`(rmdist.cpp).
>>> I first observed the problem when trying to simulate trajectories according to a DCC model fitted on my data:
>>> 1. Fitting fresh DCC models on the generated trajectories resulted in [Joint]mshape parameters that were consistently above 49.9 (due to the ceiling at 50) even though the fitted model's [Joint]mshape parameter was 5.367926.
>>> 2. Calculating the kurtosis of the trajectory innovations with `moments::kurtosis(sim at msim$simZ[[i]])` confirmed that the innovations used to progress the simulated trajectories consistently displayed a normal kurtosis of approximately 3
>>> Upon observing this behavior I decided to look under the hood. I confirmed that everything read as expected all the way down to (dccsim -> .xdccsim.fit -> .dccsim.fit -> .dccsimf -> dccsimmvt -> rmvtx -> rmvnormx) `rmvtx` and `rmvnormx`. Observing that `simZ` had a direct connection to `rmvtx` I decided to give more attention to these functions.
>>> I have not worked with Rcpp or RNGScope before, I don't know their working mechanisms. The problem might be obvious to those that are more familiar. I opted to run three experiments where I monitored the value of `rc` across multiple calls to `rmvtx`. I repeated each experiment configuration using the same set of seeds.
>>> Experiment 1: No change to the package
>>> Experiment 2: Removed the call to `rmvnormx` within `rmvtx`
>>> Experiment 3: Kept the call to `rmvnormx` within `rmvtx`. Removed the `Rcpp::RNGScope` instantiation call within `rmvnormx`
>>> In Experiment 1 it was observed that `rc` was indeed being assigned the same value across all calls to `rmvtx`.
>>> In Experiments 2 and 3 it was observed that `rc` was assigned different values across different calls to `rmvtx` as intended.
>>> It is my understanding that removing the `Rcpp::RNGScope` instantiation call within `rmvnormx` would be a safe fix for this problem since there is no random number generation within `rmvnormx` to begin with.
>>> After applying this fix I retested to confirm that the [Joint]mshape parameters of models fitted on simulated trajectories as well as the kurtosis values of the simZ for these trajectories are in line with what should be expected.
>>> My current understanding of how RNGScope works is as follows. Instantiating with `Rcpp::RNGScope scope` reads the current RNG state from R. This state is advanced as needed with any random number generation performed within the scope of the cpp function. When exiting the scope the state is written back to R.
>>> So I guess the nested RNGScope instantiation calls, where `rmvnormx` does not do any random number generation, somehow result in an RNG state that does not advance across consecutive calls to `rmvtx`. (Does the scope instantiation in `rmvnormx` read the RNG state from R again instead of from its parent scope? Does it then somehow overwrite the state for `rmvtx` before the state is written back to R?)
>>> I would appreciate any insight into the exact mechanisms that cause this bug and any feedback regarding the proposed fix.
